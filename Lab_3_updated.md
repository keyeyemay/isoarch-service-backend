Создание **веб-сервиса** для получения/редактирования данных из вашей БД. Требуется разработать все методы для реализации итоговой бизнес логики вашего приложения. Для изображений и видео `услуг` использовать `MinIO`. В `README` проекта описать все HTTP методы и таблицы с их полями.

**Требования к веб-сервису**

Методы и `url` в `API` должны строго соответствовать принципам `REST` (использовать существительные во множественном числе, правильные HTTP-глаголы). Для списка `услуг` (как в 1 лабораторной) нужно предусмотреть фильтрацию на бэкенде. Взаимодействие с БД через `ORM`. Записи в статусе `удален` на клиент не передаются (отфильтровываются на уровне запроса к БД).

Статусы нельзя менять с любого на любой: у `создателя` два разных метода (создание черновика и публикация), вернуть в `черновик` нельзя. В данной лабораторной аутентификация еще не реализована, поэтому пользователь `создатель` (текущий пользователь) зафиксирован во всех методах — укажите его константой через функцию-`singleton`. Именно этот ID используется для проверки авторства и лайков. Системные поля (ид, статусы, создатель и модератор, даты создания, формирования и завершения) передавать с клиента для изменения запрещено. Они вычисляются на бэкенде через "авторизацию" (singleton) и бизнес-логику. В начале адреса каждого метода добавьте префикс `/api`.

**Домен услуги (`/api/services`):**
- `GET /api/services` — список с фильтрацией (только опубликованные). В JSON ответа для каждой услуги необходимо добавить вычисляемое поле (например, `is_author`: 0/1). Значение 1 устанавливается, если `id` создателя услуги совпадает с `id` текущего пользователя (получаемого из функции-singleton).
- `GET /api/services/feed` — публичная лента (только опубликованные). В JSON ответа добавляется дополнительное поле (например, `is_liked`: 0/1). Оно вычисляется на бэкенде (через JOIN или подзапрос к таблице лайков) и показывает, ставил ли текущий пользователь (singleton) лайк конкретной услуге.
- `GET /api/services/draft` — получение текущего черновика (не более 1 записи для пользователя). Идентификатор услуги в URL не указывается, черновик ищется по `id` текущего пользователя.
- `POST /api/services` — создание услуги + загрузка файлов изображения и короткого видео. Файлы должны передаваться строго как бинарные данные через форму `multipart/form-data`, а не URL-ссылками. Бэкенд генерирует уникальные названия файлов на латинице (например, UUID), сохраняет сами файлы в бакет `MinIO`, а в БД записывает публичный URL объекта (или сгенерированное название файла).
- `PUT /api/services/{id}` — публикация (смена статуса на "опубликован") и обновление текстовых полей услуги.
- `DELETE /api/services/{id}` — удаление услуги. Строго **soft delete** (мягкое удаление — проставление флага `is_deleted` или `deleted_at`). Действие разрешено только автору услуги.
- `POST /api/services/{id}/like` — установка/снятие лайка текущим пользователем. В теле запроса передается JSON со значением (1 — ставит лайк, 0 — отменяет лайк).

**Домен пользователь (`/api/users`):**
- `POST /api/users/register` — регистрация
- `POST /api/users/login` — аутентификация (заглушка для 4-ой лабораторной)
- `POST /api/users/logout` — деавторизация (заглушка для 4-ой лабораторной)
