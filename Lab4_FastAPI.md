# Лабораторная работа №4 (Подробное задание для FastAPI)

## Цель работы
Завершение бэкенда для SPA. Добавление авторизации и генерация документации (Swagger) в веб-сервис на базе FastAPI.

## 1. Архитектурные требования
* **Модель взаимодействия:** AJAX + REST API + SPA.
* **Диаграмма классов бэкенда:** 1 общая диаграмма, включающая:
  * Не менее 10 методов сервиса.
  * 3 модели предметной области + База данных.
  * 4 страницы фронтенда + страница авторизации.
  * Интерфейсы сервисов должны изображаться с входной точкой и ответвлениями методов.

## 2. Требования к REST API
* **Запрет на статус в теле ответа:** Статус успеха/ошибки не должен передаваться внутри тела JSON (например, `"status": "success"` — нельзя). Статус ответа определяется строго HTTP-кодом состояния (200, 201, 400, 403, 404, 500 и т.д.).

## 3. Требования к методам API (на примере предметной области «Услуги»)

Ваша предметная область может отличаться, но она должна покрывать аналогичный по сложности функционал. Ниже приведены 10 обязательных методов.

### Домен «Пользователь»
1. `POST /auth/register` — Регистрация нового пользователя.
2. `POST /auth/login` — Аутентификация. Авторизация должна осуществляться через хранение сессий в БД/Redis и установку `Cookie`.
3. `POST /auth/logout` — Деавторизация (удаление сессии и очистка `Cookie`).

### Домен «Услуги» (или ваш целевой домен)
4. `GET /services` — Получение списка с фильтрацией (только опубликованные). В ответе должен быть флаг `$0/1$`, указывающий, является ли текущий авторизованный пользователь автором.
5. `GET /services/feed` — Публичная лента опубликованных услуг.
6. `GET /services/draft` — Получение текущего черновика (не более 1 черновика на пользователя, ID в URL не передается, определяется по сессии).
7. `POST /services` — Создание записи. **Обязательно:** автозаполнение пользователя-автора на основе текущей сессии. Также включает загрузку файлов (изображения и короткого видео) как бинарных файлов (`multipart/form-data`), а не ссылок.
8. `PUT /services/{id}` — Публикация (смена статуса на "опубликованный") и обновление полей.
9. `DELETE /services/{id}` — Удаление. Строго **soft delete** (смена статуса/пометка удаленным), разрешено только автору.
10. `POST /services/{id}/like` — Установка/снятие лайка текущим пользователем ($1$ — ставит лайк, $0$ — снимает).

## 4. Особенности реализации на FastAPI
* Для маршрутизации используйте `APIRouter`.
* Для приема бинарных файлов (изображения, видео) используйте `UploadFile` и `File(...)` из `fastapi`.
* Для работы с сессиями: устанавливайте куки через `response.set_cookie(key="session_id", value=...)` при логине, и очищайте через `response.delete_cookie(...)` при логауте.
* Проверка авторизации: создайте функцию-зависимость `get_current_user(request: Request)`, которая будет читать куки, искать сессию и возвращать пользователя. Подключайте её к закрытым эндпоинтам через `Depends(get_current_user)`.

## 5. Документирование API (Swagger)
* FastAPI генерирует Swagger автоматически (на `/docs`). Обогатите его: добавьте Pydantic-схемы для ответов (`response_model`), опишите параметры и добавьте docstring к функциям.
* **Разграничение прав в Swagger:** 
  * Без авторизации доступно только чтение-получение данных (методы `GET`).
  * С авторизацией открываются методы создателя. Для тестирования в Swagger/Postman потребуется передавать куки с Session ID вручную.
* **Демонстрация:** При показе работы преподавателю, заголовки `Cookie: session-id=<UUID>` следует прописывать в Postman вручную в разделе Headers.
