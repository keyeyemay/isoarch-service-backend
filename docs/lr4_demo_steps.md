# Показ ЛР4: скриншоты 1–9, Swagger → Postman → Redis → StarUML

В этом проекте используется **сессия Redis + cookie `session_id`**, JWT нет.
Для Postman нужен заголовок `Cookie`, вкладка Authorization — **No Auth**.

Приложение: http://localhost:8000/ · Swagger: http://localhost:8000/docs.
Используйте один адрес `localhost` во всех шагах, не меняя его на `127.0.0.1`.


| Скриншот | Что показать |
|---|---|
| 1 | POST /auth/login в Swagger, инкогнито, фактический 200 |
| 2 | GET /services в Swagger, 200 и список |
| 3 | Application → Cookies → session_id, значение для переноса |
| 4 | GET /services в Postman без cookie, 200 |
| 5 | GET /services с cookie, включённая галочка заголовка, 200 |
| 6 | PUT той же услуги без cookie, 401 |
| 7 | PUT с cookie автора, публикация, 200 |
| 8 | PUT с обновлёнными полями, 200 и новые значения |
| 9 | StarUML: signature сообщения ссылается на операцию класса |

Redis и соответствующего пользователя покажите в терминале отдельно между
API и StarUML; при необходимости сохраните дополнительный снимок Redis.

## 1. Вход в Swagger — скриншот 1

1. Откройте новое окно инкогнито Chrome/Edge (Ctrl+Shift+N).
2. Перейдите на `http://localhost:8000/docs`.
3. Если нет своей учётной записи, раскройте `POST /auth/register`, нажмите
   **Try it out**, введите приведённый JSON и нажмите **Execute**:

   ```json
   {
     "username": "lab4_demo_student",
     "password": "DemoLab4!2026",
     "full_name": "Демонстрация ЛР4"
   }
   ```

   Ожидается **201**. Если логин занят (409), выберите другой логин.
   Далее используйте именно свою пару логин/пароль.
4. Раскройте `POST /auth/login` → **Try it out**:

   ```json
   {
     "username": "lab4_demo_student",
     "password": "DemoLab4!2026"
   }
   ```

5. Нажмите **Execute**. Ожидается **200** и JSON пользователя (`id`, `username`).
   В ответе нет JWT: сервер устанавливает HttpOnly cookie.
6. **Скриншот 1:** адрес Swagger, метод `/auth/login`, отправленный JSON,
   фактический **Server response / Code 200** и тело ответа с пользователем.
   Таблица возможных Responses ниже не подтверждает выполнение запроса.

## 2. Список в Swagger и cookie — скриншоты 2–3

1. Раскройте `GET /services` → **Try it out** → **Execute**.
   Фильтры оставьте пустыми. Ожидается **200** и массив опубликованных услуг.
2. **Скриншот 2:** метод GET, URL, фактический код 200 и JSON списка.
3. Нажмите F12 → **Application** (при необходимости через `>>`) →
   **Storage → Cookies → http://localhost:8000**.
4. Найдите строку `session_id`, скопируйте целиком **Value**, то есть UUID.
   HttpOnly не мешает посмотреть значение в DevTools.
5. **Скриншот 3:** Application → Cookies, строка `session_id` с Value и HttpOnly.
   Этот UUID затем переносится в Postman; галочка у заголовка видна на снимке 5.
   В обычном ответе Swagger заголовок Set-Cookie может не отображаться:
   берите UUID из Application.

До конца демонстрации не вызывайте `/auth/logout` и не входите заново в том же
окне: logout отзывает сессию, повторный login заменяет текущий UUID.

## 3. Подготовить Postman и черновик

1. В Postman Desktop нажмите **Import** и выберите
   [`postman_demo_collection.json`](../postman_demo_collection.json).
   Это отдельная коллекция для ручного переноса cookie; исходную коллекцию
   с автоматическим login для этого показа запускать не нужно.
2. Переменных в коллекции нет: адрес, ID и cookie записаны явным текстом,
   поэтому во всех запросах значения в URL и Headers белые. Перед показом
   замените заглушки вручную:

   | Где | Заглушка | Значение |
   |---|---|---|
   | Headers → `Cookie` всех запросов с cookie | `session_id=00000000-0000-0000-0000-000000000000` | UUID из Application, без кавычек и пробелов; `session_id=` оставить |
   | URL запросов 6–8 и «Проверить сохранённую публикацию» | `/services/0` | ID черновика из ответа «Подготовка B» или «Подготовка C» |

   Серыми останутся только служебные hidden headers, которые Postman
   добавляет сам (`Host`, `User-Agent`, `Postman-Token`, `Content-Type` с boundary).

3. Запросы уже используют **No Auth** и отключённый cookie jar. Проверьте у
   каждого запроса **Settings → Disable cookie jar = ON**. Иначе Postman может
   добавить сохранённую cookie даже при снятой галочке заголовка, и «гость»
   окажется авторизованным.
   [Документация Postman](https://learning.postman.com/docs/use/send-requests/response-data/cookies).
4. Выполните **«Подготовка A. Проверить cookie из Swagger»**. Должны прийти **200** и тот же
   пользователь, что после входа в Swagger.
5. В **Headers** авторизованных запросов уже есть строка:

   ```http
   Cookie: session_id=<UUID>
   ```

   Галочка слева от строки должна быть включена. Это включает отправку заголовка.
   Не вставляйте `HttpOnly`, `Path`, `SameSite` или весь заголовок Set-Cookie.
6. Выполните **«Подготовка B. Создать собственный черновик»**:
   **Body → form-data**: `title` — Text, `image` и `video` — **File**.
   Если Postman не нашёл относительные пути, выберите вручную файлы проекта:
   `static/images/default_signature.png` и `static/videos/default_signature.mp4`.
   Content-Type для multipart вручную не задавайте: Postman добавит boundary.
   Ожидается **201**. Запомните `id` из ответа и подставьте его вместо `0` в URL запросов 6–8.
7. Если получен **409 Draft already exists**, выполните запрос **«Подготовка C»**:
   он возвращает свой черновик; возьмите его `id`. Если ответ `null`, создайте
   черновик запросом «Подготовка B». Не берите произвольный ID из публичного списка:
   для успешного PUT запись должна принадлежать текущему пользователю.

## 4. Список не требует cookie — скриншоты 4–5

Выполните **«4. Все опубликованные услуги — БЕЗ cookie»**.
Должен вернуться **200**, массив услуг, `is_creator: 0` для гостя.

**Скриншот 4:** GET `http://localhost:8000/services`, Headers без Cookie,
фактический **200 OK** и JSON списка.

Затем выполните **«5. Все опубликованные услуги — С cookie»**.
**Скриншот 5:** GET, строка Cookie с включённой галочкой, 200 и JSON списка.
Дополнительно можно выполнить запрос с неверной cookie: он также даёт **200**. При действующей сессии могут отличаться
`is_creator` и `is_liked`, но публичный список доступен во всех трёх случаях.
В этом задании «все услуги» — все **опубликованные**, без черновиков и удалённых.

## 5. Публикация гостем запрещена — скриншот 6

Выполните **«6. PUT гостя — отказ 401»**:

```http
PUT http://localhost:8000/services/<ID черновика>
Content-Type: application/json
```

Cookie отсутствует, cookie jar выключен. Тело **Body → raw → JSON**:

```json
{
  "title": "Опубликовано через Postman",
  "description": "Смешанный рацион. Демонстрация публикации.",
  "delta_n15": 9.4,
  "delta_c13": -18.2
}
```

Ожидается **401 Unauthorized**, `{"detail":"Authentication required"}`.
**Скриншот 6:** PUT, URL с ID, отсутствие Cookie в Headers, фактический 401 и ответ.
В этом приложении **401** означает отсутствие сессии, а **403** — попытку
авторизованного пользователя изменить чужую запись.

## 6. Автор успешно публикует и обновляет — скриншоты 7–8

Выполните **«7. PUT автора — публикация 200»** с тем же ID и телом.
В Headers включён `Cookie: session_id=<UUID>` с UUID, вставленным вручную.

Ожидается **200 OK**. В ответе видны обновлённые поля, `status: "published"`,
`is_creator: 1`, `creator_id`, совпадающий с пользователем, и `formed_at`.

**Скриншот 7:** PUT с ID, включённая галочка у Cookie, фактический 200 и поля ответа.
Выполните **«8. PUT автора — повторное обновление 200»**: он изменяет описание и
`delta_n15` на `10.5`. **Скриншот 8:** новый JSON в Body, фактический 200 и
обновлённые поля в Response. Дополнительный запрос «Проверить сохранённую
публикацию» читает запись заново и подтверждает сохранение.

## 7. Показать Redis и пользователя в терминале — отдельный показ

Откройте терминал в корне проекта (в том же Linux/WSL, где запущен Docker).
Сначала покажите команды Redis:

```bash
docker compose exec redis redis-cli PING
docker compose exec redis redis-cli --scan --pattern 'isoarch:session:*'
```

Ожидается `PONG` и ключи вида `isoarch:session:<SHA-256>`.
Ключ содержит хеш UUID, а значение — ID пользователя. Чтобы найти **именно
сессию из вашего Swagger**, запустите:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m scripts.show_session
```

Вставьте скопированный UUID и нажмите Enter. Ввод скрыт. Скрипт ничего не меняет:
он покажет ключ Redis, результат GET (`user_id`), TTL в секундах и соответствующие
`id`, `username`, `full_name` пользователя из PostgreSQL. Пароль не выводится.

Затем подставьте напечатанный ключ вместо `isoarch:session:HASH` и выполните
команды напрямую, чтобы на снимке были видны Redis CLI и его ответы:

```bash
docker compose exec redis redis-cli GET 'isoarch:session:HASH'
docker compose exec redis redis-cli TTL 'isoarch:session:HASH'
```

При необходимости подтвердите пользователя прямым SQL-запросом. Замените `7`
на фактический ID из Redis GET:

```bash
docker compose exec postgres psql -U isoarch_user -d isoarch_db -c "SELECT id, username, full_name FROM users WHERE id = 7;"
```

Список логинов всех активных сессий выводит Lua-скрипт, выполняемый внутри Redis:

```bash
docker compose exec redis redis-cli EVAL "$(cat services/active_logins.lua)" 1 isoarch:usernames 'isoarch:session:*'
```

Ответ — пары «логин, число сессий». Скрипт перебирает ключи `isoarch:session:*`
командой SCAN, читает `user_id` и берёт логин из хеша `isoarch:usernames`,
который сервер заполняет при входе: Lua не имеет доступа к PostgreSQL.
Сессии, созданные до этой доработки, показываются как `user_id=<ID>`.

Снимок терминала должен показывать: ключ, ID пользователя, положительный TTL
и тот же username, что на скриншоте 1. `GET = nil` или `TTL = -2` означает, что
сессии уже нет: снова войдите и скопируйте новый UUID.

После всех снимков можно вызвать `POST /auth/logout` в Swagger: ключ этой
сессии исчезнет, а запрос Postman `/auth/me` со старой cookie получит 401.


## 8. Диаграмма последовательности в draw.io — скриншот 9

Откройте [lr4_sequence.drawio](../lr4_sequence.drawio) в draw.io / diagrams.net.

- **Лист 01:** фронтенд и два домена, все восемь HTTP-запросов и ответы.
  У каждого запроса указаны HTTP-маршрут и вызов операции с arguments в скобках.
  БД и нативного приложения на диаграмме нет.
- **Лист 02:** классы доменов и их операции. Номера 1–8 соответствуют шагам
  последовательности; остальные операции API показаны без номера.

Для проверки связи выделите стрелку запроса, например публикации (шаг 5),
и откройте данные элемента. В них сохранены:

- `signature` — `ServiceDomain.publish_draft(id: int, pub_data: PublishRequest): ServiceResponse`;
- `operationRef` — `op-publish_draft`, ID операции на листе 02;
- `arguments` — `d, {description, delta_n15, delta_c13}`;
- `receiverRef` — `service-head`, линия жизни домена услуг.

У линии жизни есть `classifierRef`, указывающий на класс домена листа 02.
Подписи сообщений получаются из сигнатур операций и аргументов. Для проверки
и обновления всех связей выполните из корня проекта:

```bash
python3 scripts/sync_sequence_diagram.py
```

Скрипт проверяет существование операций и совпадение домена-получателя,
копирует сигнатуры операций в сообщения и обновляет подписи вызовов.
При изменении метода редактируйте `signature` у операции листа 02, а затем
запустите синхронизацию. Обновляется `.drawio`; PNG/SVG-превью после ручных
изменений нужно экспортировать заново из редактора.

**Скриншот 9:** покажите выбранное сообщение с данными `signature`, `operationRef`
и `arguments`. Лист 02 можно показать дополнительным снимком для сопоставления
с методом класса. [Превью последовательности](lr4_sequence_preview.png).

Здесь связь реализована средствами документа draw.io и проверяется скриптом;
это не нативная модель StarUML. По содержанию показаны те же домены, операции,
аргументы и последовательность HTTP-взаимодействий.

## 9. Запуск и выключение проекта

Команды выполняются в терминале Linux/WSL из корня проекта. Docker должен быть запущен.

### Подготовка при первом запуске

Если виртуальное окружение ещё не создано или зависимости не установлены:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

### Запуск

1. Запустите PostgreSQL, Redis, MinIO и Adminer и дождитесь их готовности:

   ```bash
   docker compose up -d --wait
   ```

2. В том же терминале запустите FastAPI:

   ```bash
   .venv/bin/python -m uvicorn main:app --host 0.0.0.0 --port 8000
   ```

   Дождитесь `Application startup complete` и сообщения о запуске Uvicorn.
   Терминал оставьте открытым. Миграции и подготовка демонстрационных данных
   в пустой БД выполняются автоматически.

3. Откройте приложение: http://localhost:8000/.
   Для демонстрации откройте в инкогнито http://localhost:8000/docs.
   Команды Redis из раздела 7 выполняйте во втором терминале из корня проекта.

Если порт 8000 уже занят работающим экземпляром приложения, используйте его
или остановите его через Ctrl+C в соответствующем терминале перед повторным запуском.

### Выключение

1. В терминале с Uvicorn нажмите **Ctrl+C** и дождитесь завершения приложения.
2. Остановите контейнеры из корня проекта:

   ```bash
   docker compose down
   ```

   Данные PostgreSQL, файлы MinIO и данные Redis сохраняются в Docker volumes.
   Для обычного выключения используйте команду без `-v`: этот флаг удаляет volumes.

Для следующего запуска повторите два шага из подраздела «Запуск»;
повторная установка зависимостей не требуется.
