# Подготовка к защите ЛР4 — IsoArch

Этот материал объясняет, что сделано в проекте, как это работает и зачем нужно. Примеры относятся к текущему коду. Числа `7` и `42` в примерах условные: на демонстрации нужно брать реальные ID из ответов API.

**Главное:** у нас вход по логину и паролю, cookie `session_id` в браузере и серверная сессия в Redis. JWT, SSO, двухфакторная аутентификация и RSA в прикладном коде не реализованы. Ниже они объясняются как теория и возможное развитие проекта.

## 1. Что можно сказать в начале защиты

> В лабораторной работе я доработал серверную часть приложения IsoArch для публикации изотопных исследований. Пользователь может просматривать исследования, фильтровать список, создавать черновик с изображением и видео, публиковать и редактировать свою запись, удалять её и ставить лайки.
>
> Основная задача ЛР4 — добавить настоящий вход и разграничить доступ. После проверки пароля сервер создаёт сессию в Redis и передаёт браузеру её идентификатор через cookie. Каталог и лента доступны гостям, а изменения требуют входа. Изменять и удалять запись может только её автор.
>
> Фронтенд работает как SPA и обращается к FastAPI через HTTP-запросы. Основные данные хранятся в PostgreSQL, файлы — в MinIO, сессии — в Redis. Для проверки API используются Swagger и Postman. Диаграмма последовательности показывает путь от входа до публикации и лайка.

## 2. Предметная область и цель работы

IsoArch — учебный веб-сервис изотопных исследований костных останков. В задании используется общее слово «услуга», а у нас ему соответствует запись об исследовании. Поэтому API называется `/services`, хотя в интерфейсе показаны исследования.

У записи есть название, описание, значения `delta_n15` и `delta_c13`, изображение, видео и автор. Эти численные показатели относятся к изотопному составу образца. Приложение хранит и показывает результаты, а не вычисляет научные выводы по ним.

В ЛР4 требовалось связать интерфейс, API, пользователей и права доступа в работающий сценарий. До этого нельзя было считать фиксированного пользователя полноценной авторизацией: сервер должен сам устанавливать, кто отправил запрос, и проверять его права.

Мы реализовали регистрацию, вход, выход, срок жизни сессии, публичное чтение и защищённые операции. Дополнительно оформили схемы запросов и ответов, документацию Swagger, демонстрационную коллекцию Postman и диаграммы.

## 3. Из каких частей состоит проект

| Часть | Простое объяснение | Роль в нашем проекте |
|---|---|---|
| SPA на JavaScript | Страница обновляет своё содержимое без полной перезагрузки | Каталог, лента, черновик, редактирование, вход и регистрация |
| FastAPI | Сервер принимает HTTP-запросы и возвращает ответы | Проверяет входные данные, пользователя и права, вызывает логику операций |
| PostgreSQL | База связанных таблиц | Хранит пользователей, исследования и лайки |
| Redis | Быстрое хранилище по ключу | Хранит связь между сессией и пользователем с ограниченным сроком жизни |
| MinIO | Хранилище файлов, совместимое с S3 | Хранит изображения и видео |
| SQLAlchemy | Связь Python-объектов с таблицами | Читает и изменяет записи PostgreSQL |
| Alembic | Управление изменениями схемы БД | Применяет миграции при запуске |
| Swagger UI | Интерактивная документация API | Позволяет выполнять запросы из браузера на `/docs` |
| Postman | Отдельный клиент для HTTP-запросов | Позволяет явно управлять заголовками и демонстрировать права доступа |
| Docker Compose | Запуск нескольких сервисов одной командой | Поднимает PostgreSQL, Redis, MinIO и Adminer |

FastAPI запускается отдельно через Uvicorn. Adminer — вспомогательный веб-интерфейс для просмотра PostgreSQL.

Путь обычного запроса:

```text
SPA / Swagger / Postman
        → HTTP-запрос → FastAPI
        → проверка данных и сессии
        → бизнес-правила
        → нужное хранилище
        → HTTP-код и ответ клиенту
```

Не каждый запрос использует все хранилища. Например, просмотр каталога гостем не требует поиска сессии в Redis, если cookie вообще не передана.

### SPA, AJAX и REST API

**SPA** — Single Page Application, одностраничное приложение. Каталог и лента выглядят как разные страницы, но JavaScript меняет содержимое одного документа. В нашем коде этим занимается `static/js/spa.js`.

**AJAX** — способ получать данные с сервера без полной перезагрузки страницы. У нас используется `fetch`, ответы обычно приходят в JSON. Несмотря на букву X в названии AJAX, XML для этого не обязателен.

**REST API** в рамках работы означает интерфейс ресурсов: GET читает, POST создаёт или выполняет действие, PUT публикует и обновляет, DELETE удаляет. У нас есть серверное состояние входа в Redis, поэтому на защите лучше говорить «HTTP API в стиле REST», а не утверждать, что реализованы абсолютно все ограничения строгого REST.

### Три основные модели

- `User` — пользователь. Содержит ID, логин, хеш пароля и дополнительные данные.
- `IsotopicSignature` — исследование. Содержит поля записи, автора, ссылки на файлы и состояние.
- `SignatureLike` — связь пользователя с понравившейся публикацией.

Один пользователь может создать много исследований. На одну публикацию пользователь может поставить только один лайк: пара «пользователь — исследование» уникальна в БД.

## 4. Какие запросы реализованы и зачем

| Запрос | Назначение | Кто может выполнить |
|---|---|---|
| `POST /auth/register` | Создать учётную запись | Гость |
| `POST /auth/login` | Проверить пароль и создать сессию | Гость |
| `POST /auth/logout` | Отозвать текущую сессию и очистить cookie | Повторный выход также допустим |
| `GET /auth/me` | Узнать пользователя текущей сессии | Вошедший пользователь |
| `GET /services` | Получить опубликованные исследования с фильтрами | Все |
| `GET /services/feed` | Получить первую публикацию ленты | Все |
| `GET /services/feed/{id}?next=true` | Получить следующую публикацию | Все |
| `GET /services/draft` | Получить свой черновик | Вошедший пользователь |
| `POST /services` | Создать черновик с изображением и видео | Вошедший пользователь |
| `PUT /services/{id}` | Опубликовать или обновить запись | Только автор |
| `DELETE /services/{id}` | Пометить запись удалённой | Только автор |
| `POST /services/{id}/like` | Поставить или снять свой лайк | Вошедший пользователь |

**GET не означает автоматически публичный доступ.** Каталог и лента публичные, но свой черновик и `/auth/me` требуют входа. Регистрация и вход, наоборот, доступны гостю, хотя используют POST.

### Фильтрация

Пример: `GET /services?c13_max=-15&filter=Бронза`.

`filter` ищет по названию, `c13_max` задаёт верхний порог показателя δ¹³C. Сервер возвращает только опубликованные записи. У гостя `is_creator=0`; у автора своей записи — `is_creator=1`. Это числовой флаг, позволяющий интерфейсу показать нужные кнопки. Однако права всё равно проверяются на сервере.

### Черновик и медиафайлы

При `POST /services` передаются `title`, `image`, `video` в формате `multipart/form-data`. Изображение и видео отправляются содержимым файлов, а не строками со ссылками.

FastAPI принимает их через `UploadFile`. Сервер проверяет файлы и сохраняет их в MinIO, а в PostgreSQL хранит запись и ключи файлов. Ограничения проекта: изображение до 10 МиБ, видео MP4 до 64 МиБ и 60 секунд.

Автор берётся из сессии. Передать чужой `creator_id` при создании нельзя: разрешены только три указанных поля формы.

У пользователя может быть не больше одного черновика. Это проверяется логикой сервиса и уникальным индексом БД. Если черновик уже есть, повторное создание даёт 409. Запрос `/services/draft` не содержит ID пользователя: сервер сам находит его по сессии. Если черновика нет, возвращается `null`.

### Публикация, обновление и удаление

Пример тела `PUT /services/42`:

```json
{
  "title": "Исследование образца",
  "description": "Описание результатов исследования",
  "delta_n15": 9.4,
  "delta_c13": -18.2
}
```

Сервер проверяет владельца, обновляет поля и переводит черновик в `published`. Повторный PUT позволяет исправить опубликованную запись. Автор и дата первоначальной публикации сохраняются. `title` необязателен: если его не передать, старое название останется.

Удаление — **soft delete**, то есть логическое удаление. Строка остаётся в БД, но получает `status="deleted"` и пропадает из публичных ответов. Это сохраняет историю и связи.

### Лента и лайки

`GET /services/feed` возвращает одну первую публикацию. Запрос с ID и `next=true` возвращает следующую по ID, а после последней — первую. Черновики и удалённые записи в ленту не входят.

`POST /services/42/like` с `{"like":1}` ставит лайк, с `{"like":0}` снимает. Повторная передача 1 не создаёт второй лайк. Ответ содержит состояние лайка и общее число лайков.

### HTTP-коды и поле status

| Код | Как объяснить на примере проекта |
|---|---|
| 200 | Запрос успешно выполнен: список получен, пользователь вошёл, запись обновлена |
| 201 | Создан пользователь или черновик |
| 204 | Операция выполнена без тела ответа: выход или удаление |
| 401 | Нет действующей сессии либо неверный логин/пароль |
| 403 | Пользователь вошёл, но пытается изменить чужую запись |
| 404 | Запись отсутствует или недоступна в этом публичном запросе |
| 409 | Конфликт: например, уже существует черновик или занят логин |
| 413 | Загружаемый файл слишком большой |
| 422 | Неверные поля или недопустимое содержимое файла |
| 503 | Не доступно необходимое хранилище сессий или медиа |

Запрет задания относится к обёрткам `{"status":"success"}` и `{"status":"error"}`: результат операции сообщает HTTP-код. Поле услуги `status="published"` обозначает состояние самой записи, поэтому это другой смысл.

## 5. Контрольный вопрос: что такое cookie?

**Короткий ответ:** cookie — небольшое значение, которое браузер хранит для сайта и отправляет в подходящих запросах. Сервер устанавливает его заголовком `Set-Cookie`, клиент возвращает заголовком `Cookie`. Параметры cookie определяют срок и условия отправки. [Объяснение MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies).

### Пример нашего проекта

После успешного `POST /auth/login` сервер отправляет примерно такой заголовок:

```http
Set-Cookie: session_id=<случайный UUID>; HttpOnly; Max-Age=86400; Path=/; SameSite=lax
```

В следующих запросах браузер передаёт:

```http
Cookie: session_id=<тот же UUID>
```

UUID здесь — случайный идентификатор сессии. В нём нет логина, пароля или прав доступа.

Параметры в `api/users_api.py`:

| Параметр | Зачем он нужен |
|---|---|
| `HttpOnly` | Не позволяет JavaScript страницы читать cookie через `document.cookie` |
| `SameSite=Lax` | Ограничивает отправку cookie в межсайтовых сценариях |
| `Path=/` | Разрешает использование cookie на путях всего приложения |
| `Max-Age=86400` | Задаёт срок хранения в браузере: сутки по умолчанию |
| `Secure` | Включается настройкой `SESSION_COOKIE_SECURE=1` для работы через HTTPS |

Локально используется HTTP, и `Secure` по умолчанию выключен. `HttpOnly` не мешает видеть cookie в DevTools и не запрещает браузеру отправлять её автоматически.

Само наличие `HttpOnly` не обеспечивает полную защиту от вредоносного JavaScript, а `SameSite=Lax` не стоит называть универсальной защитой от всех межсайтовых атак.

В браузере значение смотрим в **Application → Cookies → http://localhost:8000 → session_id → Value**. В Postman переносим только UUID в заголовок `Cookie: session_id=<UUID>`. Атрибуты `HttpOnly`, `Path` и `SameSite` туда не копируем.

Тонкость: наша cookie обслуживает сессию приложения, но имеет `Max-Age`. Поэтому в терминологии браузера это cookie с заданным сроком хранения, а не cookie, обязательно исчезающая при закрытии обычного окна.

**Фраза для защиты:** «Cookie хранит у клиента идентификатор. Кто за ним стоит, определяет сервер через Redis».

## 6. Контрольный вопрос: что такое сессия?

**Короткий ответ:** сессия — серверный способ помнить, что пользователь уже вошёл. Вместо передачи пароля при каждом действии клиент передаёт выданный идентификатор.

### Как проходит вход у нас

1. Пользователь отправляет логин и пароль в `POST /auth/login`.
2. Сервер находит пользователя в PostgreSQL и проверяет пароль.
3. `create_session()` создаёт случайный UUID.
4. Сервер вычисляет SHA-256 от UUID.
5. В Redis записывается `isoarch:session:<хеш UUID> → user_id` с TTL.
6. Исходный UUID отправляется браузеру в cookie `session_id`.

В JSON возвращаются данные пользователя без пароля. JWT в ответе нет.

### Как проверяется следующий запрос

```text
Cookie с UUID
  → SHA-256(UUID)
  → GET isoarch:session:<хеш> в Redis
  → ID пользователя
  → пользователь из PostgreSQL
  → проверка прав на операцию
```

Эту цепочку организуют `services/auth.py` и `api/dependencies.py`. `get_current_user` применяется к закрытым операциям через `Depends`. Если пользователь не найден, запрос получает 401.

Для публичных запросов есть `get_optional_user`: без сессии можно читать данные, с действующей сессией появляются персональные флаги.

### Как заканчивается сессия

- При выходе удаляется ключ Redis, а браузеру отправляется очистка cookie.
- По истечении TTL сессия перестаёт действовать автоматически.
- При повторном входе заменяется сессия, переданная в текущем запросе. Сессии других браузеров автоматически не удаляются.

В проекте TTL по умолчанию равен 86400 секундам и задаётся `SESSION_TTL_SECONDS`. Обычные запросы не продлевают его: время считается с создания сессии.

**Зачем хранить хеш UUID?** Чтобы содержимое Redis не содержало готовый исходный идентификатор, который можно сразу подставить в cookie. При запросе сервер легко вычисляет хеш снова. Это не заменяет защиту самого Redis от постороннего доступа.

**Cookie и сессия — не одно и то же:** cookie находится у клиента, а наша сессия находится на сервере. Удалить cookie вручную — не значит отозвать сессию: её копия ещё может работать до TTL. Поэтому logout удаляет и серверную запись.

**Фраза для защиты:** «Сессия связывает случайный идентификатор с пользователем и имеет срок жизни. Logout отзывает её на сервере».

## 7. Контрольный вопрос: что такое Redis?

**Короткий ответ:** Redis — хранилище данных с быстрым доступом по ключу. Оно работает преимущественно в оперативной памяти и может сохранять данные на диск. У нас Redis отвечает за сессии.

Условный пример записи:

```text
Ключ:     isoarch:session:<SHA-256 от UUID>
Значение: 7
TTL:      85000 секунд
```

Это означает: данный идентификатор относится к пользователю с ID 7 и действует ещё указанное время. Пароль, имя пользователя и исследования в этой записи не хранятся.

Redis удобен здесь потому, что сессию нужно быстро находить, удалять при выходе и автоматически прекращать по времени. Хранить сессии в PostgreSQL тоже возможно; в этой работе выбран Redis.

### Команды для демонстрации

Команды выполняются из корня проекта в Linux/WSL:

```bash
docker compose exec redis redis-cli PING
docker compose exec redis redis-cli --scan --pattern 'isoarch:session:*'
```

`PING` должен вернуть `PONG`. Вторая команда показывает ключи сессий. Для нужного ключа:

```bash
docker compose exec redis redis-cli GET 'isoarch:session:HASH'
docker compose exec redis redis-cli TTL 'isoarch:session:HASH'
```

Вместо `HASH` нужно подставить реальный хеш. `GET` возвращает ID пользователя. Положительный TTL — оставшиеся секунды, `-2` — ключа нет, `-1` — ключ существует без срока истечения. В норме наши сессии имеют срок.

Чтобы найти именно сессию из браузера и показать её пользователя:

```bash
.venv/bin/python -m scripts.show_session
```

Скрипт попросит UUID скрытым вводом, вычислит ключ, покажет ID, TTL и данные пользователя из PostgreSQL. Он не создаёт сессию и не продлевает её.

В `docker-compose.yml` включены AOF и volume. AOF записывает изменения для восстановления Redis после перезапуска, а volume сохраняет данные отдельно от контейнера. Это не делает сессии бессрочными: TTL продолжает ограничивать их жизнь.

При недоступности Redis запрос, которому нужна проверка сессии, получает 503. Сервер не должен молча считать уже переданную сессию гостем при отказе хранилища. Запрос публичного каталога вообще без cookie не требует Redis для поиска сессии.

**Фраза для защиты:** «PostgreSQL хранит предметные данные, Redis — временные сессии, MinIO — файлы».

## 8. Контрольный вопрос: что такое JWT?

**Короткий ответ:** JWT — формат токена с набором утверждений, например об идентификаторе пользователя и сроке действия. Часто используется подписанный JWT из трёх частей: `header.payload.signature`. Подпись защищает от незаметного изменения содержимого, но сама по себе не скрывает его. JWT также может применяться в зашифрованной форме. [Стандарт JWT, RFC 7519](https://www.rfc-editor.org/rfc/rfc7519).

В обычном подписанном JWT заголовок описывает алгоритм, payload содержит данные, а signature позволяет проверить подлинность. Base64url-кодирование первых частей не является шифрованием. Пароли туда помещать нельзя.

Сервер должен проверять подпись и ожидаемый алгоритм, срок действия и необходимые условия применения токена, например издателя и получателя. Просто прочитать payload недостаточно.

### Сравнение с нашим проектом

| Вопрос | Наша сессия | Возможный вариант с подписанным JWT |
|---|---|---|
| Что получает клиент? | Случайный UUID | Токен с данными и подписью |
| Где связь с пользователем? | В Redis | Может находиться в payload |
| Как проверяется? | Поиск сессии и пользователя | Проверка подписи и утверждений токена; возможны дополнительные проверки БД |
| Как немедленно отозвать? | Удалить ключ Redis | Нужен отдельный механизм отзыва либо ожидание истечения срока |
| Что передаём сейчас? | `Cookie: session_id=<UUID>` | Такой вариант в проекте не реализован |

Если бы мы выбрали JWT, после входа клиент мог бы получать токен и отправлять `Authorization: Bearer <JWT>`. Но текущий API так не работает: подставить наш UUID в Bearer-заголовок недостаточно.

**Cookie и JWT не взаимоисключающие варианты:** cookie — способ хранения и передачи значения, JWT — формат значения. JWT тоже можно передавать в cookie. У нас в cookie хранится непрозрачный UUID, а не JWT.

**Фраза для защиты:** «JWT знаю как альтернативный формат токена, но в ЛР использована требуемая серверная сессия в Redis».

## 9. Контрольный вопрос: аутентификация и авторизация

**Аутентификация** отвечает на вопрос «Кто вы?». **Авторизация** — «Что вам разрешено?».

Ещё есть **идентификация**: пользователь сообщает, кем представляется, например вводит логин. Одного логина недостаточно для подтверждения личности.

Пример с записью №42, которую создал пользователь №7:

1. Вход по логину и паролю подтверждает пользователя №7 — это аутентификация.
2. Cookie позволяет серверу узнать его в следующих запросах.
3. При `PUT /services/42` сервер сравнивает `creator_id` записи с ID пользователя — это авторизация.
4. Если оба равны 7, изменение разрешено.
5. Если вошёл другой пользователь, возвращается 403.
6. Если действующей сессии нет, возвращается 401.

Проверка владельца находится в `owned_service()` в `services/isotopic_signatures.py`. Проверка выполняется и для публикации, и для удаления.

Скрытая кнопка на странице не защищает данные: пользователь может отправить запрос через Postman. Поэтому проверка на сервере обязательна.

Регистрация — создание учётной записи. Она отличается от входа. Наш API `/auth/register` сам не выдаёт сессию; фронтенд после регистрации отдельно выполняет login.

**Фраза для защиты:** «Пароль подтверждает, кто пользователь, а сравнение с автором записи определяет, может ли он её изменить».

## 10. Контрольный вопрос: что такое SSO?

**Короткий ответ:** SSO — Single Sign-On, единый вход. Пользователь входит через общий центр учётных записей и может пользоваться несколькими подключёнными приложениями без повторного ввода пароля в каждом.

Один из способов реализации — OpenID Connect: приложение доверяет проверку личности провайдеру, а затем проверяет полученный результат входа. OpenID Connect добавляет аутентификацию поверх OAuth 2.0; сам OAuth 2.0 прежде всего посвящён делегированию доступа. [Объяснение OpenID Foundation](https://openid.net/developers/how-connect-works/).

### Как это могло бы выглядеть для IsoArch

Это пример расширения, которого сейчас в проекте нет:

1. Пользователь нажимает «Войти через университет».
2. IsoArch направляет его в университетский центр входа.
3. Центр проверяет пользователя или использует уже существующий вход.
4. IsoArch получает и проверяет результат по протоколу.
5. Внешняя учётная запись связывается с локальным пользователем.
6. IsoArch создаёт свою сессию в Redis и устанавливает cookie.

Права автора по-прежнему проверяет IsoArch: успешный университетский вход не даёт права редактировать любые исследования.

Перенос cookie из Swagger в Postman не является SSO. Мы просто используем одну сессию одного сервиса в другом HTTP-клиенте.

**Фраза для защиты:** «SSO позволяет нескольким приложениям доверять общему входу. В нашем проекте пока собственная проверка логина и пароля».

## 11. Контрольный вопрос: двухфакторная аутентификация

**Короткий ответ:** 2FA — подтверждение входа двумя разными типами факторов. Например, пароль — то, что пользователь знает, а приложение с одноразовыми кодами на телефоне — то, чем он владеет. Два пароля не являются двумя разными факторами. [Описание факторов в NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html).

Обычно различают знание секрета, владение устройством и биометрическую характеристику. Практическая схема должна проверять независимые факторы, а не просто два раза просить одинаковые данные.

### Пример возможного расширения проекта

Сейчас login проверяет только логин и пароль. Чтобы добавить 2FA, можно было бы организовать такой процесс:

1. Проверить пароль.
2. Создать короткоживущую запись о незавершённом входе.
3. Запросить одноразовый код из приложения-аутентификатора.
4. Проверить код, ограничить число попыток и не допускать повторного использования уже принятого кода.
5. Только после этого выдать обычную сессию, позволяющую публиковать записи.

Незавершённый вход нельзя считать полноценной авторизованной сессией. Иначе проверку второго фактора можно будет обойти.

Наша cookie после входа не является вторым фактором: она подтверждает уже выполненный вход. Копирование cookie в Postman тоже не превращает вход в двухфакторный.

**Фраза для защиты:** «В работе однофакторный вход по паролю. При 2FA полноценная сессия выдавалась бы только после второго независимого подтверждения».

## 12. Контрольный вопрос: что такое RSA?

**Короткий ответ:** RSA — асимметрический криптографический алгоритм. У него есть открытый и закрытый ключи. На его основе существуют схемы шифрования и цифровой подписи. Для практического применения нужны стандартизованные схемы, а не вычисления “чистого RSA”. [Спецификация RSA, RFC 8017](https://www.rfc-editor.org/rfc/rfc8017).

Два разных назначения:

| Действие | Что происходит |
|---|---|
| Шифрование | Данные шифруются открытым ключом получателя; расшифровать их должен владелец закрытого ключа |
| Подпись | Владелец закрытого ключа создаёт подпись; открытым ключом проверяют её подлинность |

Подпись не скрывает сообщение. Её задача — подтверждать источник и обнаруживать изменение. Не стоит объяснять подпись просто как «шифрование всего сообщения закрытым ключом»: это отдельная схема.

### Связь с нашим проектом

RSA в текущем прикладном коде нет. Для паролей используется scrypt, для ключей сессий — SHA-256. Это хеширование, а не RSA и не обратимое шифрование.

Гипотетический пример: при переходе на JWT с подписью RS256 центр входа подписывал бы токен закрытым RSA-ключом, а IsoArch проверял бы подпись открытым. Серверу проверки не понадобился бы закрытый ключ центра входа.

На локальной демонстрации используется HTTP. Поэтому нельзя утверждать, что наше соединение сейчас защищено RSA или HTTPS. Кроме того, HTTPS не означает обязательное применение RSA: конкретные алгоритмы зависят от TLS-настройки.

**Фраза для защиты:** «RSA использует пару ключей и может участвовать в подписи токенов. У нас пароль защищён scrypt, а сессия проверяется через Redis».

## 13. Как мы храним пароли и почему это не шифрование

В `services/auth.py` используется scrypt со случайной солью для каждого пароля. В БД сохраняется строка вида:

```text
scrypt$<соль>$<результат вычисления>
```

При входе сервер берёт сохранённую соль, повторяет вычисление с введённым паролем и сравнивает результаты. Восстанавливать исходный пароль для проверки не требуется.

Соль нужна, чтобы одинаковые пароли разных пользователей не имели одинаковый сохранённый результат. Она не обязана быть секретной. scrypt делает массовый перебор паролей более затратным по вычислениям и памяти.

SHA-256 используется в другом месте — для случайных идентификаторов сессий. Нельзя делать вывод, что обычный быстрый SHA-256 без специальной схемы подходит для хранения пользовательских паролей: пароли часто гораздо легче угадать, чем случайный UUID.

| Термин | Назначение | Пример в работе |
|---|---|---|
| Кодирование | Представить данные в другом формате | JSON представляет поля запроса; base64url упоминается при объяснении JWT |
| Хеширование | Получить результат для сравнения без штатного обратного восстановления | scrypt пароля, SHA-256 идентификатора сессии |
| Шифрование | Скрыть данные с возможностью расшифровать по ключу | В текущем локальном HTTP-сценарии транспортное шифрование не настроено |
| Цифровая подпись | Подтвердить подлинность и целостность | RSA-подпись JWT — только теоретический пример расширения |

Подробные действия находятся в [инструкции демонстрации](lr4_demo_steps.md). Здесь — смысл каждого доказательства.

## 15. Как объяснить диаграммы

В проекте есть [общая диаграмма архитектуры и классов](lr4_architecture.md) и [диаграмма последовательности draw.io](../lr4_sequence.drawio). Они отвечают на разные вопросы: первая показывает устройство системы, вторая — порядок действий.

На первом листе draw.io три участника: фронтенд SPA, домен пользователей и домен услуг. Здесь «домен» — область ответственности приложения, а не интернет-адрес. Оба домена реализованы внутри одного FastAPI-приложения, это не отдельные микросервисы.

В коде обработчики — функции `APIRouter`. Имена `UserDomain` и `ServiceDomain` на диаграмме группируют их логически; отдельных Python-классов с такими именами в приложении нет.

Время идёт сверху вниз. Сплошная стрелка показывает запрос, пунктирная — ответ. Сценарий содержит восемь шагов: вход, список с фильтрацией, создание с файлами, чтение черновика, публикация, первая запись ленты, следующая запись и лайк.

БД не показана именно на Sequence по требованию сценария. Это не означает, что приложение работает без БД: хранилища отражены на общей диаграмме.

На втором листе draw.io перечислены операции доменов. В сообщениях сохранены `operationRef`, `signature`, `arguments`, а у линий жизни — `classifierRef`.

- `signature` — описание метода: имя, параметры и тип результата.
- `arguments` — конкретные значения, передаваемые в данном шаге.
- `operationRef` — ссылка на операцию второго листа.

Например, метод `publish_draft(id, pub_data)` вызывается для конкретного черновика `d` с набором полей. Здесь слово `signature` означает сигнатуру метода и не связано с криптографической подписью RSA.

Связи проверяются и подписи обновляются командой:

```bash
python3 scripts/sync_sequence_diagram.py
```

Это реализация связей средствами draw.io и скрипта, а не нативная модель StarUML. Если спросят про редактор, нужно прямо назвать draw.io. При буквальном требовании использовать StarUML замена формата требует согласования.

## 16. Частые дополнительные вопросы

**Почему нельзя передавать user_id вместо сессии?**

Потому что ID легко узнать или подставить. Он обозначает пользователя, но не доказывает право действовать от его имени. Сервер получает ID из проверенной сессии.

**Почему UUID не является JWT?**

UUID у нас — случайный непрозрачный идентификатор. В нём нет payload и криптографической подписи токена. Его смысл хранится в Redis.

**Почему публичный список одинаково доступен с cookie и без неё?**

Таково правило доступа. Cookie нужна для персональных флагов, а не для разрешения чтения каталога. Опубликованные записи видны всем, черновики и удалённые — нет.

**Можно ли получить свой черновик без ID в URL?**

Да. Сервер узнаёт пользователя по сессии и находит его единственный черновик. Это и требуется заданием.

**Почему сохраняем файлы отдельно от PostgreSQL?**

MinIO отвечает за содержимое файлов, PostgreSQL — за структуру записи и связи. API возвращает адреса медиа для показа в браузере.

**Зачем Pydantic и response_model?**

Pydantic проверяет поля, типы и ограничения. `response_model` задаёт публичную структуру ответа и участвует в документации. Например, модель ответа пользователя не содержит хеша пароля.

**Swagger и Postman обходят защиту?**

Нет. Они отправляют обычные HTTP-запросы и проходят те же проверки, что SPA. Swagger генерируется из OpenAPI-описания; Postman позволяет отдельно управлять заголовками и телом запроса.

**Почему в коллекциях Postman нет переменных?**

Переменная `{{...}}` подсвечивается цветом, и из запроса не видно, что именно уходит на сервер. Поэтому адрес, ID и `Cookie: session_id=<UUID>` записаны явным текстом, и значения во всех запросах белые. UUID из `Set-Cookie` вставляется вручную. Серыми остаются только служебные заголовки, которые Postman добавляет сам.

**Где используется Lua в Redis?**

Скрипт `services/active_logins.lua` возвращает логины пользователей с активными сессиями. Он выполняется командой `EVAL` целиком внутри Redis и атомарно: перебирает ключи `isoarch:session:*` через SCAN, читает `user_id` и берёт логин из хеша `isoarch:usernames`. Этот хеш сервер заполняет при входе, потому что из Lua нельзя обратиться к PostgreSQL. Сам вход по-прежнему использует MULTI/EXEC: там нужна только атомарная группа команд без логики.

**Проверяет ли сервер автора только при создании?**

Нет. При создании автор устанавливается по сессии, а при PUT и DELETE заново сравнивается с текущим пользователем. Иначе можно было бы изменить чужую запись, подставив её ID.

**Гарантирует ли скрытая кнопка безопасность?**

Нет. Она улучшает интерфейс, но реальное ограничение находится в серверной проверке.

**Означает ли закрытие инкогнито logout?**

Нет. После завершения приватного сеанса браузер очищает его локальные данные, но серверная сессия может оставаться до TTL. Для явного отзыва нужен `/auth/logout`.

**Почему нельзя сказать, что JWT всегда безопаснее сессий?**

Безопасность зависит от всей реализации. Сессии удобно отзывать в Redis; JWT удобно проверять по подписи, но немедленный отзыв требует отдельного решения. Для этой ЛР сессии соответствуют выбранной архитектуре и заданию.

3. Cookie содержит случайный UUID; Redis связывает его хеш с ID пользователя.
4. Срок сессии по умолчанию — сутки, logout удаляет её на сервере.
5. Каталог и лента публичные; черновик, создание и лайки требуют входа; PUT и DELETE требуют авторства.
6. 401 — нет действующей сессии, 403 — нет прав на чужую запись.
7. Файлы загружаются бинарно через multipart и хранятся в MinIO.
8. Пароли хешируются scrypt, UUID — SHA-256. Это разные задачи.
9. JWT, SSO, 2FA и RSA объясняем как теорию, не выдаём за реализованные функции.
10. Диаграмма draw.io показывает последовательность запросов и ссылки на операции доменов.

Для запуска и выключения используйте раздел 9 [инструкции демонстрации](lr4_demo_steps.md). Перед показом проверьте `/docs`, актуальность cookie и принадлежность записи текущему пользователю.
